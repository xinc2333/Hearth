# 世界玩法设计

本文是「世界」玩法的设计稿：在一座按上海的结构等比缩小的城市澜江市里，模拟现实中的生活。它建在跑团之上（见[跑团设计](tabletop.md)）。

实现进度：第 15 节的第 1、2 步已经完成（城市和地图、开局、时间、移动、身体、钱、场景、约定的检查），第 3～5 步还没做。没做的部分仍是设计，做完后按现状改写。

## 0. 目标和原则

- **从现实出发，不写死规则。** 程序里没有「旷工三天就辞退」这类规则。现实里事情怎么发生，就怎么模拟：人有身体、有钱、有约定、有自己知道的事；有人发现事情和预期不一样，就按自己的性格和处境做出反应。
- **程序管物理，AI 管人心。** 时间、路程、身体、钱这类有客观规律的，由程序计算。一个人察觉到什么、会怎么想、怎么做，由 AI 替他决定。
- **每个人只知道他该知道的。** 程序记录每个人知道什么、从哪里知道的。AI 替一个人做决定时，只给它这个人知道的事。
- **一次请求只做一件事。** 宁可多几次请求，也不让一次请求同时处理很多人和事，以免出错和编造。
- **所有请求都接在预设的请求后面。** 和跑团一样：先由预设拼好完整的请求（小猫之神这类带请求脚本的预设，由它的脚本处理），Hearth 只在末尾追加这一步的说明和数据。说明本身也是预设里的条目。
- **只给模型看相关的。** 城市、人物和记录都按这一步需要什么挑选。数据有多长，取决于这一幕，不取决于城市有多大、玩了多久。
- **沿用跑团。** 属性、特长、状态、对主角的态度和结算，都照跑团的规则。
- **城市只有一座。** 澜江市由 Hearth 自带。

## 1. 架构

世界分四层：

| 层 | 内容 | 谁负责 |
| --- | --- | --- |
| 物理 | 时间、地点和路程、天气、身体（饱、精力、健康）、钱（只在账户之间转移，不会凭空出现或消失） | 程序按客观规律计算 |
| 约定 | 人和人、人和单位之间的约定：劳动合同、租房、上学、约会、借钱、承诺。每份约定写明谁对谁有什么期待，以及按惯例落空了会怎样 | AI 在开局和剧情里建立，程序保存和检查 |
| 认知 | 每个人知道什么：亲眼看到的、别人告诉的、自己推测的，带时间和来源 | 程序记录信息怎么传开，AI 补充推测 |
| 心智 | 每个人怎么想、怎么做：按性格、身体、处境、所知和对别人的态度做决定 | AI，每次只替一个人 |

世界这样运转：

```
程序推进时间
  │
  ├─ 检查期待：约定里写明「某人某时在某地」「某日前付款」，到点没有发生，就是期待落空
  ├─ 检查身体：饿了、困了、病了
  ├─ 送达信息：消息、电话、当面说的话
  ├─ 计划到点：某人计划里的下一件事
  │
只把「某人察觉到的事」交给这个人
  │  察觉要有条件：上司在公司才会发现你没来；睡着的人收不到消息
  │
AI 替他决定做什么：等一等、发消息、打电话、上门、扣钱、报警、改计划……
  │
程序执行他的行动：移动要花时间，付钱要有余额，发消息要有联系方式
  │
行动产生新的事实，又被别人察觉……
```

- 程序只认这四种「察觉」：期待落空、身体越线、收到信息、计划到点。旷工、欠租、失联都没有专门的代码，它们从约定、认知和心智里自然产生（例子见第 8 节）。
- **随机性由程序提供。** 现实里大多数日子平平常常，偶尔有意外。程序每天给每位重要人物掷一次「意外骰」：大多是平常的一天，少数有点事，极少有大事。AI 按掷出的程度写他这一天，避免天天出大事。
- **常识由 AI 提供。** 一家公司对旷工怎么处理、房东会宽限几天、什么情况下会报警，AI 按现实中国大城市的常理，结合约定里写的惯例和这个人的性格来判断。

## 2. 一轮怎么跑

```
你发消息
  │
第一步：裁定（1 次请求）
  │  跑团的检定，加上这一轮过去多久、主角去不去别处、怎么去
  ├─ 程序定下这一轮的时间段（例如 08:30 → 09:40），按时间顺序走一遍，找出谁察觉到了什么
  ├─ 到了新的地方，或者这里来了新的人：场景（1 次请求），写出主角看到的人（第 6 节）
  │
第二步：反应（察觉到事情的人各 1 次，同时发出；没有人察觉就跳过）
  │  AI 替这个人决定做什么，程序执行。牵涉主角、发生在这段时间里的，成为这一轮的事件
  │  行动又让别人察觉到事情时，再跑一轮，最多两轮，之后的留给下一轮
  │
第三步：叙述（1 次）
  │  按检定结果和这一轮的事件写正文，写到时间段的结尾
  │
第四步：结算（1 次，在后台）
  │  跑团的结算，加上主角这边的事：花了钱、吃饭睡觉、新的约定、告诉了谁什么、在场的人看到了什么
  │
第五步：每日推演（跨过一天时，每位不在场的重要人物各 1 次，在后台）
     他这一天怎么过的、心情和关系的变化、明天的打算、要不要联系主角
```

- **时间以裁定定下的时间段为准。** 剧情走得更远时（例如主角睡着了），结算可以往后推，多出来的时间里的事留给下一轮。时间不会往回退。
- **单轮上限**：不是跳过时间时（第 5 节），一轮最多 3 小时。
- **换一版回复、继续写**：沿用这一轮的裁定和反应，时间段和事件不变。
- **开着「检定绝对通过」**：没有裁定，时间由结算报告，反应和事件留给下一轮。
- **聊天模式**（直接和 AI 聊天）：整轮不跑跑团，也不跑世界。

## 3. 开局

侧栏的「新建世界：澜江市」会新建一个世界对话。「澜江市」是 Hearth 自带的一张角色卡，第一次用时自动加到角色卡列表里，带「世界」标签。在它上面新建对话时，先出现开局页：

| 项 | 说明 |
| --- | --- |
| 名字 | 默认用当前用户角色的名字 |
| 性别、年龄 | |
| 职业 | 上班族、学生、自由职业、无业，再写一句具体做什么，例如「广告公司的设计」 |
| 住在哪 | 选一个区，或者交给 AI 按职业和收入挑 |
| 关于主角 | 外貌、性格、经历，随便写，可以不写 |
| 开始时间 | 默认 2026-03-02（星期一）07:30 |

点「开始」后，开局作为这个对话的第一次生成来跑：先发一次请求（接在预设的请求后面，强制调用 `hearth_setup`），模型写出：

- 属性和特长（按跑团的参照表）
- 工作或学业：单位、职位、收入，以及劳动合同或学籍这份约定，包括单位的惯例（考勤、请假、发薪）
- 住处：租房时还有房东和租房合同
- 余额和生活习惯：作息、吃饭和花钱的习惯
- 身边的人：上司和同事、房东、一两位家人，作为「相关的人」（第 7 节）

接着同一次生成写出开场（「世界·开场说明」）：从开始时间、主角在家的样子写起，带出今天的安排，写到主角可以开始行动的地方。

- 生成的数值不需要确认就生效，之后可以在「跑团」页里改。
- 主角的介绍存成这个对话专用的用户角色，对话绑定它，不影响别的对话。开局没有完成时，开局页留着，再点「开始」重来，用的还是同一个用户角色。
- 当前预设还没有跑团和世界的条目时，「开始」会顺带加上，页面上写明这一点。预设里少了某一条世界条目时，用 Hearth 自带的那一条。
- 开局页出现时不显示输入框：世界从开局开始，不从一条消息开始。

## 4. 澜江市

### 按上海缩小

- **结构照上海**：水系、海岸线、各区的位置和分工、环路和地铁的走向，都照上海的样子。
- **距离按 1:2 缩小**：面积是上海的四分之一，人口按同样的密度缩小。比例是一个参数，可以改。
- **速度照现实**：步行、骑车、地铁、开车的速度不缩小，所以通勤比上海短。
- **物价照上海**：工资、房租、餐饮、交通按上海的水平，房租从市中心往外递减。
- **地名是虚构的。**

### 概况

| 项 | 内容 |
| --- | --- |
| 定位 | 中国东部沿海的特大城市。东临东海，北临沧江入海口，南临南湾 |
| 人口 | 常住约 620 万 |
| 范围 | 陆地约 1600 km²（含沧洲岛），东西约 50 km，南北约 45 km |
| 地形 | 平原，海拔只有几米；西南有一片 100 m 左右的小山 |
| 气候 | 亚热带季风。春季多雨，6～7 月梅雨，7～9 月有台风，夏季最高可达 38°C 以上，冬季湿冷，最低约 −2°C |

### 地点

地图上有约 80 个写好的地标，每个记下名字、坐标、类型、营业时间和一句话简介，所属的区按坐标算出。住宅、小店、小饭馆这类日常地点，按各区的人口和特点补在地标和地铁站周围。

| 类型 | 例子 |
| --- | --- |
| 住处 | 老公房、石库门弄堂、新小区、江景公寓、郊区别墅 |
| 工作 | 写字楼、科学城园区、工厂、港口、商店、医院、学校 |
| 生活 | 菜市场、超市、便利店、银行、派出所 |
| 吃喝 | 餐馆、小吃街、咖啡馆、酒吧 |
| 玩 | 公园、景点、商场、电影院、体育馆、海滩、乐园 |
| 交通 | 地铁站、火车站、码头、机场 |

- 剧情里出现地图上没有的地点（例如老街上一家书店），结算把它登记为新地点，放在最近的已知地点旁边，地图上随之出现。
- 大的地点可以分区，例如「澜江大学 · 图书馆」「星衡广告 · 12 楼」。同一地点的分区之间不算路程。

## 5. 时间

- **精度**：分钟。界面上显示「第 3 天 · 3 月 4 日 星期三 08:15」。
- **怎么走**：只在你发消息时往前走（第 2 节）。没有实时的钟，关掉 Hearth 后世界不会自己运转。
- **跳过时间**：在剧情里直接说「睡到明早 7 点」「接下来一周照常上班」。程序逐段推进，期间的期待、反应和推演照常发生，最后让模型写一段概述。一次最多跳 30 天。快进期间主角按自己的作息过，除非你另有说明。
- **天气**：程序按月份的气候每天抽一次天气（晴、多云、阴、小雨、大雨、雷阵雨、雾、台风）和气温，提前生成 3 天，手机里能看预报。
- **一时情绪的回落**：跑团里每轮回落 15%。世界里改为按游戏时间，每小时回落 3%，大约一天回落一半。

## 6. 地点、移动和场景

- **位置**：每个人都有位置。主角精确到地点；重要人物和相关的人按各自的计划和剧情；路人只记最后见到的地方，以及常出现的地点（例如咖啡馆的店员）。
- **移动**：主角要去别处时，裁定里写目的地和方式，程序按下表算用时和费用。

| 方式 | 用时 | 费用 |
| --- | --- | --- |
| 步行 | 直线距离 × 1.3 ÷ 4.5 km/h | 0 |
| 骑车 | 直线距离 × 1.3 ÷ 12 km/h，加 3 分钟取车 | 每 30 分钟 1.5 元 |
| 地铁 | 走到最近的站 + 等车（半个发车间隔）+ 车上的时间（按线路的平均速度，含停站）+ 每次换乘 5 分钟 + 出站走到目的地 | 按里程 3～8 元 |
| 公交 | 打车用时 × 1.8，加等车 8 分钟 | 2 元 |
| 打车 | 等车 5 分钟 + 直线距离 × 1.4 ÷ 车速（高峰 18 km/h，平时 28 km/h，夜间 40 km/h） | 按计价规则 |
| 开车 | 同打车，不用等车，加停车 5 分钟 | 每公里 0.7 元 |

- 裁定没写方式时，按主角的生活习惯挑；习惯里也没有，就挑最快的、付得起的。
- 地铁停运的时间里不能坐地铁。
- 同行的在场角色跟着一起移动。
- 车费自动从余额里扣，记进账目。

### 场景：这里有谁

到了一个地方，你看到的是这里此刻的人，完全从主角的视角写：

> 推门进去，咖啡馆里人不多。吧台后面是个扎马尾的店员，二十五六岁，正在打奶泡；靠窗的位子上坐着一个女生，看起来二十出头，米色风衣，耳机挂在脖子上，在翻一本很厚的书……

这里有哪些人，由程序先定下来：

| 谁 | 怎么来的 |
| --- | --- |
| 认识的人 | 重要人物和相关的人，按他们此刻的计划在这里 |
| 这里的工作人员 | 店员、保安、前台。每个地点第一次去时生成；之后在他们上班的时间去，见到的是同一批人 |
| 来来往往的人 | 程序按地点的类型、时段、星期、天气和所在的区，算出这里大概有多少人、什么年纪、男女、来做什么，每人还有一个停留时长。例如工作日下午的咖啡馆，附近上班的人、学生、自由职业者居多 |

- **人多的地方**（商场、车站、广场）只写人流的程度，加上离主角最近、最显眼的几个人，最多 8 个。
- **只写看得到的**：定下这些人以后，Hearth 发一次请求（强制调用 `hearth_scene`），模型写出每个人大概的年纪、性别、身材、穿着、显眼的特征、在做什么、在哪个位置。不写名字、身份和心里在想什么。
- **写进正文**：叙述时，这一幕的人交给模型，正文用第一视角写出来。
- **人会来来去去**：在同一个地方待着时，程序按停留时长让人离开、按时段补进新的人，只为新来的人再发一次场景请求。
- **散场**：主角离开后，没打过交道的人就散了。说过话、有过来往的，由结算登记成路人；问到了名字，以后就用名字称呼。

「这里」页列出这一幕的人。不知道名字的用描述称呼，例如「靠窗看书的女生（二十出头，米色风衣）」。点某个人的「设为重要人物」，Hearth 按模板补全他的档案（第 9 节）：名字、身份、背景、性格，外貌和已经看到、听到的一致。从这时起，他有了自己的住处、工作、作息和所知。

## 7. 人

### 四类人

| 类别 | 是谁 | 心智 |
| --- | --- | --- |
| 主角 | 你扮演的人 | 由你决定 |
| 重要人物 | 你指定的人，最多 8 位 | 有。察觉到事情时反应，每天推演 |
| 相关的人 | 和主角有约定、或者被卷进事情的人：上司、同事、房东、家人、办案的警察 | 有，只在察觉到事情时反应，不每天推演 |
| 路人 | 其余遇到的人，包括场景里看到的人 | 没有，只记看得到的样子和打过的交道 |

- 路人被卷进事情时（例如和主角约好了明天见面），自动成为相关的人。
- 相关的人有一段一两百字的简介和性格系数，在他第一次成为相关的人时生成。

### 每个人有什么

| 数据 | 主角 | 重要人物 | 相关的人 | 路人 |
| --- | --- | --- | --- | --- |
| 属性、特长、状态 | 有（跑团） | 有 | 有 | 有 |
| 身份和职业 | 有 | 有 | 有 | 一句话 |
| 位置 | 精确到地点 | 按计划和剧情 | 按计划和剧情 | 最后见到的地方 |
| 身体 | 饱、精力、健康，按小时 | 精力、健康，按天 | 无 | 无 |
| 心情、压力 | 无（由你扮演） | 有 | 无 | 无 |
| 钱 | 余额和账目 | 经济状况和月收入 | 经济状况 | 经济状况 |
| 约定 | 有 | 有 | 和主角有关的 | 无 |
| 所知 | 无（就是你知道的） | 有 | 有 | 无 |
| 对主角的态度 | — | 有（跑团） | 有（跑团） | 有（跑团） |
| 对其他人的态度 | — | 只对其他重要人物 | 无 | 无 |
| 档案 | 开局时的介绍 | 按模板的完整档案和摘要 | 简介 | 场景里看到的样子 |

- **经济状况**分五档：拮据、紧张、普通、宽裕、富有。只有主角记具体余额。
- **主角没有对别人的态度**，和跑团一样，由你在剧情里表达。
- **重要人物之间的态度**用跑团的六条线加熟悉度，分方向记（A 对 B、B 对 A 各一份）。只在两人互相认识时建立，只在受到影响时更新：反应、结算或每日推演里，两人一起经历了某件事。

### 身体

身体按客观规律随时间变化，由程序计算：

| 项 | 怎么变 | 越线时 |
| --- | --- | --- |
| 饱（0～100） | 每小时 −6；吃一顿正餐 +50，吃点东西 +20 | 低于 30 饿了，低于 10 饿得发慌 |
| 精力（0～100） | 清醒时每小时 −5，干体力活或熬夜时更快；睡觉每小时 +12 | 低于 30 困倦（属性 ×0.9），低于 10 极度疲惫（×0.7） |
| 健康（0～100） | 受伤、生病时下降，休息和治疗时回升 | 低于 60 带病，低于 30 需要就医 |

- 「饿了」「困了」这些越线是身体发出的信号：对主角，交给叙述写出来；对重要人物，交给每日推演。
- 吃了什么、睡了多久，由结算报告。快进时按生活习惯算。

### 钱

- **余额**：手机支付和银行卡合在一起算。现金很少用到，不单独记。
- **钱只会转移**：每一笔都是从谁到谁、多少、为什么。付不起就付不成，剧情里的事也就做不成。
- **固定的收支来自约定**：工资是劳动合同里公司对主角的付款期待，房租是租房合同里主角对房东的付款期待。到期时程序照约定转账；付款方之前在反应里决定过扣钱、推迟或拒付的，按他的决定。
- **其他收支**：车费由程序扣；吃饭、购物、请客、接活的收入由结算记下。

### 所知

- 每个有心智的人都有一份「所知」：发生了什么、什么时候、从哪知道的（亲眼看到、谁告诉的、自己推测的）。
- 信息这样传开：在场的人看到了什么，由结算记下；消息和电话把内容带给对方；反应和推演里，一个人告诉了别人什么，对方就知道了。
- AI 替一个人做决定时，只给它这个人的所知。主角做过的事，别人不在场、也没人告诉他，他就不知道。
- 每人保留最近 40 条；更早的在每日推演里归进一段「长期记忆」。

## 8. 约定

### 约定长什么样

```yaml
名称: 劳动合同
双方: [主角, 星衡广告]
代表: { 星衡广告: 王经理 }
期待:
  - { 谁: 主角, 做: 在场, 地点: 星衡广告, 时间: 工作日 09:00–18:00 }
  - { 谁: 星衡广告, 做: 付款, 给: 主角, 金额: 14000, 时间: 每月 10 日 }
惯例: 迟到当天扣 50 元；无故旷工按日薪三倍扣；连续旷工三天公司可以解除合同；事假要提前一天和上司说
记录: []
```

- **期待**是程序能检查的事：某人某时在某地（在场）、某日前付某笔钱（付款）、某时前做完某事（截止，由结算或反应报告做没做完）。
- **惯例**是一段文字，写这类约定在现实里通常怎么处理。它只是参考，落空时怎么办由对方的心智决定：同样是迟到，宽厚的上司可能一笑了之。
- **谁建立约定**：开局时 AI 建立工作、租房等约定；剧情里答应的事由结算记下；反应和推演里，一个人也可以和别人建立、修改或解除约定（上司解除合同、房东宽限几天、重要人物约朋友吃饭）。
- **落空时告诉谁**：能察觉到的人。在场的期待落空，告诉当时在那个地点的对方的人；付款落空，告诉收款的一方；截止落空，告诉等着的一方。

### 现实里的事怎样产生

| 现实里的事 | 怎样发生 |
| --- | --- |
| 旷工 | 劳动合同期待主角 9:00 在公司。主角没到，在公司的上司和同事察觉。同事也许发消息问；上司按公司的惯例、自己的脾气和对主角的态度，决定打电话、记旷工还是先等等。主角一直不来，每天都会落空，上司的决定随之升级，可能扣钱，也可能解除合同 |
| 发工资 | 合同期待公司每月 10 日付款。程序照约定转账；上司之前决定过扣钱的，按他的决定扣 |
| 欠租 | 租房合同期待主角每月 1 日付房租。余额不够，期待落空，房东察觉。催、宽限、上门，取决于房东的性格和处境 |
| 爽约 | 约会期待两人 19:00 在酒馆。主角没到，等在那里的对方察觉：等一会儿、发消息、走人，对主角的态度随之变化 |
| 失联和调查 | 林晚给主角发了消息，期待他回复。迟迟没回，她察觉，打电话，没人接。每日推演里她越来越担心，决定去他家看看；敲门没人，又联系他的公司，得知他两天没上班；于是报警，和警方建立「立案调查」的约定。办案的警察成为相关的人，按办案的常理一步步查：去最后出现的地方，问认识他的人，问到的是这些人真正知道的事 |

这些都没有专门的代码。

## 9. 重要人物

### 名额

最多 8 位。满了以后要先取消一位，才能再设一位。

### 怎么产生

- **从剧情里升级**：在「这里」页、「人物」页或地图上，给遇到过的人点「设为重要人物」。刚在场景里看到、还不知道名字的人也可以。
- **新建**：写一段介绍，或者贴进已有的人物档案，也可以从已导入的角色卡里选一个角色。贴进来的档案原样保留，模型只补程序要用的部分。

升级或新建时，Hearth 发一次请求（强制调用 `hearth_profile`），模型按这个人在剧情里已有的表现写出：

- 按模板的完整档案（2000～3000 字）和摘要（150～250 字）
- 属性、特长、性格系数（已有的保留）
- 住处和工作单位：从地图上选，或者登记新地点
- 每周作息，以及他的工作、租房等约定
- 经济状况和月收入
- 他已经知道的事（从剧情里他在场的部分整理）
- 和其他重要人物的初始态度（认识的才写）

结果直接生效，可以在「人物」页修改，或者点「重新生成」。

### 档案模板

| 部分 | 内容 |
| --- | --- |
| 基本信息 | 姓名、年龄、性别、身份 |
| 外貌 | 身高体型、发型、五官和标志性特征、不同场合的穿着 |
| 背景 | 出身、教育、经历、现在的生活和经济 |
| 兴趣爱好 | 喜欢做什么，做到什么程度 |
| 人际关系 | 家人、朋友、和其他重要人物的关系 |
| 语料 | 几组问答，展示他怎么说话。只作参考，不是发生过的事 |
| 性格 | 底色、主色调、点缀、对冲四层，每层几条衍生和一条反向衍生 |
| 理解 | 这些性格怎样切换和共存、行为的边界、在什么条件下露出哪一面、和主角相处的原则 |

性格分四层、另写一段「理解」，是为了让模型把人演成几种特质的组合，而不是一个标签。

### 取消

取消重要人物后，档案和所知保留，以后再设为重要人物时不用重写。他退回相关的人（和主角有约定时）或路人，不再每天推演，地图上不再显示。他和其他重要人物之间的态度保留，但不再更新。

### 每日推演

跨过一天时，每位不在场的重要人物各发一次请求（强制调用 `hearth_day`）。交给模型的是这个人自己的东西：完整档案、身体、心情和压力、所知、这一天的作息和约定、这一天他察觉到的事、意外骰的结果、他对主角和其他重要人物的态度。模型替他写出：

- 这一天怎么过的：几件事，平常的一天就写平常的事
- 心情、压力、精力和健康的变化
- 新知道的事和推测
- 对其他重要人物的态度变化（受到影响的才写）
- 明天的打算：作息有没有调整，要不要约人、要不要去哪
- 要不要联系主角：什么时候、怎么联系、为什么、说什么

联系主角没有次数上限，也没有公式，由他按自己的心情、牵挂和处境决定。程序给他参考的事实，例如「距上次和主角联系 3 天」「主角上一条消息还没回」。

一次跳过多天时，每人只发一次请求，覆盖这几天，每天各掷一次意外骰。

## 10. 手机

- **联系人**：剧情里交换过联系方式的人，由结算记下。开局生成的上司、同事、房东和家人自带。
- **消息**：时间、谁、内容、有没有回。别人发来的消息由他的反应或推演写出原文；主角发出的消息由结算记下。保留最近 100 条。
- **日程**：作息、约定和截止的事。
- **天气**：今天和之后两天。

## 11. 每一步交给模型什么

每一步都是：预设拼好的请求，末尾追加这一步的说明（预设条目）和数据。

| 步骤 | 追加的说明 | 追加的数据 |
| --- | --- | --- |
| 裁定 | 跑团·裁定说明、世界·裁定补充 | 跑团数据；时间、天气、主角的位置和身体、今天的安排；在场的人 |
| 场景 | 世界·场景 | 这个地点的简介、时间和天气；程序定下的人（认识的人、工作人员、来往的人各自的年纪段、性别、来做什么）；已经描述过的人照原样带上 |
| 反应 | 世界·人物反应 | 这个人：摘要、身体、心情、所在、所知、和别人的约定、对主角的态度；他察觉到的事 |
| 叙述 | 跑团·叙述说明、世界·叙述补充 | 检定结果；这一轮的时间段和事件；主角所在地点的详情；在场重要人物的完整档案；其余同裁定 |
| 结算 | 跑团·结算说明、世界·结算补充 | 接在叙述的请求和刚写好的回复后面；跑团数据和世界数据 |
| 每日推演 | 世界·每日推演 | 见第 9 节 |
| 人物档案 | 世界·人物档案 | 这个人在剧情和记录里出现过的内容 |
| 开局 | 世界·开局 | 开局页填的内容、城市概况 |

- **主角不知道的事**（别人背后做的事、不在场的人的近况）在叙述的数据里标出「主角不知道」，要求只通过主角看得到、听得到的方式体现，和暗骰一样。
- **替一个人做决定时**，说明里写明「他只知道下面这些事；聊天记录里他不在场的部分，他不知道」。
- **城市概况**（约 800 字）写在「澜江市」这张角色卡的描述里，每轮不变，能用上缓存。地图只给你看，不发给模型。
- **正文里不出现数值**：时间、钱可以自然地写（「快九点了」「打车花了三十多」），属性、身体和态度的数值不写。

### 预设条目

| 条目 | 标记 |
| --- | --- |
| 世界·裁定补充 | `<<<\|hearth\|world-ruling>>>` |
| 世界·场景 | `<<<\|hearth\|world-scene>>>` |
| 世界·人物反应 | `<<<\|hearth\|world-act>>>` |
| 世界·叙述补充 | `<<<\|hearth\|world-narrate>>>` |
| 世界·结算补充 | `<<<\|hearth\|world-settle>>>` |
| 世界·每日推演 | `<<<\|hearth\|world-day>>>` |
| 世界·人物档案 | `<<<\|hearth\|world-profile>>>` |
| 世界·开局说明 | `<<<\|hearth\|world-setup>>>` |
| 世界·开场说明 | `<<<\|hearth\|world-opening>>>` |

- 和跑团的条目一样，由插件取走，不按普通条目发送。
- 每一条都可以带一句 `*-lead`（例如 `<<<|hearth|world-act-lead>>>`）：用预设自己的口吻，接在这一步前面。
- Hearth 自带一套通用的条目。适配过的预设（例如本地的小猫之神适配版）带自己口吻的条目和 lead。

## 12. 费用

| 情况 | 请求次数 |
| --- | --- |
| 平常的一轮，没有人察觉到什么 | 3（裁定、叙述、结算） |
| 到了新的地方，或者这里来了新的人 | 再加 1 次（场景） |
| 有人察觉到事情 | 再加每人 1 次，最多两轮 |
| 跨过一天 | 再加每位不在场的重要人物 1 次，在后台 |
| 设为重要人物、新建重要人物 | 1 |
| 开局 | 1 |

- 每次请求的前面都是同一份预设请求和聊天记录。接口支持缓存时，这部分按缓存的价格计费，通常便宜很多，多出来的主要是末尾这一步。
- 反应只发给察觉到事情的人。平常的时间里没人察觉，就不发。
- 路人没有心智，不发请求。
- 反应同时发出；结算和每日推演在后台进行，不耽误你看正文。

## 13. 界面

- **状态条**：输入框上方一行，例如「第 3 天 · 3 月 4 日 星期三 08:15 · 小雨 · 梧桐区 徐坊 · 余额 4,230 元」，后面是饱和精力的小图标。
- **事件条**：回复上方，和检定条放在一起，例如「09:20 王经理发来消息」。点开看详情。
- **结算提示**：回复下方，在跑团的基础上加上世界的变化，例如「余额 −36 元（打车）」「到达 中城区 江滩」「新约定：周五 19:00 和林晚在小酌酒馆」。
- **场景条**：到了新的地方时，回复上方显示一行，例如「到达 衡梧路 · 梧桐里咖啡 · 7 个人」。
- **检查器新增四页**：
  - 「这里」：所在地点的简介和营业时间，这一幕的人（第 6 节），附近的地点。
  - 「地图」：能缩放、拖动的示意地图，画出水系、区、环路、地铁和地点，标出你、重要人物和约定的地点。点地点看简介，点人看位置和近况。
  - 「人物」：重要人物和相关的人（位置、近况、档案、约定、彼此的态度），他们的所知默认收起；「设为重要人物」「取消重要人物」「新建重要人物」。
  - 「手机」：联系人、消息、日程、天气预报。
- **开局页**：见第 3 节。
- 界面上不用表情符号，地图上的地点用简单的图形区分类型。

## 14. 实现

### 放在哪里

世界是跑团插件里的一个模式，代码放在 `src/plugins/tabletop/world/`。对话的角色卡是「澜江市」时启用。原因：人物数据和跑团是同一份，插件之间又不能互相引用代码。

| 文件 | 内容 |
| --- | --- |
| `world/city/` | 澜江市的数据：水系、区、环路、地铁、地点、气候，坐标按上海的尺度记，载入时按比例缩小 |
| `world/clock.ts` | 日期、星期、天气、意外骰 |
| `world/route.ts` | 路线、用时、费用 |
| `world/body.ts` | 身体的变化和越线 |
| `world/ledger.ts` | 账目和转账 |

### 数据存放

| 内容 | 存在哪里 |
| --- | --- |
| 澜江市的地理、交通、地点、气候 | 插件代码里的数据，不存进对话 |
| 世界的实时状态：时间、天气、位置、身体、账目、约定、所知、手机、事件记录、新登记的地点、心情和压力、重要人物之间的态度 | 每个回复版本上，和跑团的实时状态在一起 |
| 重要人物名单和档案、相关的人的简介 | 对话上（`chat.plugins.tabletop.world`），走修改通道，可以撤销 |
| 开局设置 | 对话上 |
| 主角的介绍 | 这个对话专用的用户角色 |
| 这一幕的人、各地点的工作人员 | 每个回复版本上，和实时状态在一起 |
| 本轮的时间段、反应和事件 | 这条回复消息上，和裁定在一起，所有版本共用 |

每个回复版本存一份完整的实时状态，换版本、开分支时自动切换。为了控制对话文件的大小：所知每人 40 条，消息 100 条，事件记录 100 条，态度只记互相认识的人。

### 内核需要的支持

第 1、2 步没有改内核：

- 「澜江市」角色卡由窗口通过导入接口加上（`world/card.ts`），主角的用户角色通过已有的接口新建。
- 开局作为第一次生成来跑，所以开局请求和其他步骤一样接在预设的请求后面。
- 界面（开局页、状态条、到达和事件、「这里」「地图」「手机」三页）和跑团的界面一样随主程序发布，所以世界玩法要发新版本，不能只靠插件更新。

还需要的：

1. 插件能在生成之外拿到这个对话按预设组装好的请求（包括预设请求脚本处理后的），用于每日推演，以及 Hearth 重启后的后台步骤（现在重启后「重新结算」要等这个对话再生成一次才行）。

### 风险

| 风险 | 对策 |
| --- | --- |
| AI 的反应不合常理，或者事事都很戏剧化 | 说明里要求按现实常理；意外骰决定这一天有没有事；约定的惯例和数值作为依据 |
| 一个人知道了不该知道的事 | 所知单独列出，说明里强调；结算记下谁看到了什么 |
| 请求变多、变慢 | 反应同时发出，结算和推演在后台；没人察觉时不发 |
| 一件事引出一连串反应 | 每轮最多两轮反应，之后的留给下一轮 |
| 正文和状态对不上，例如正文说她回家了，计划说她在上班 | 在场的人以结算为准，不在场的人以程序为准；叙述说明要求按世界数据写 |
| 对话文件变大 | 记录有上限；以后改成每个回复版本只存变化 |

### 测试

| 测试什么 | 内容 |
| --- | --- |
| 物理 | 时间、天气、路线的用时和费用、地铁停运、身体的变化、转账和余额不足 |
| 约定 | 在场、付款、截止三种期待的检查；落空时告诉谁 |
| 认知 | 在场的人记下看到的事、消息和告诉带来的传播；只给这个人他的所知 |
| 心智 | 用模拟的模型接口：挑出察觉到事情的人、执行行动、两轮上限、每日推演 |
| 挑选 | 交给模型的数据只含这一步需要的 |
| 整轮 | 模拟接口跑几天游戏时间：五步的顺序、事件进正文、结算记账、快进 |
| 真实模型 | 用测试密钥跑一个游戏周：旷工、欠租、约会这几件事能不能自然发生，反应合不合常理，每轮的请求次数和花费 |

## 15. 实现顺序

1. **城市和地图**：按上海缩小的地理、区、环路、地铁、地点，示意地图和路线计算。
2. **物理、场景和约定**：开局、时间和天气、身体、钱、移动、场景（这里有谁）、约定的检查，接进跑团的三步。
3. **心智和认知**：相关的人的反应、所知的记录和传播、手机。做完这一步就能玩：在澜江市上班过日子，旷工、欠租会自然引出后果。
4. **重要人物**：升级、取消、新建，档案，每日推演，主动联系，彼此的态度，地图上的位置。
5. **细化**：用真实模型跑长一些的游戏时间，调说明和数值。

## 16. 以后可以做

- **城市新闻和公共事件**：台风、交通事故、展会，影响出行和人的计划。
- **物品**：手机没电、丢了钥匙、买东西。
- **节假日和调休**。
- **后台步骤用更便宜的模型**，例如结算和每日推演。
- **每个回复版本只存变化**，减小对话文件。
