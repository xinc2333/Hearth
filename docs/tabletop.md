# 跑团设计

本文说明跑团插件的规则和实现，对应 0.6.0 及之后的版本。第 0～10 节是规则和体验，第 11 节是实现。预设怎样接入跑团，见[预设适配](presets.md)。

## 0. 目标和原则

- **目的是让剧情更真实、更生动。** 数值只是依据，本身不是看点，一切从主角的视角出发。
- **数值由程序计算。** 掷骰、成功率、数值增减、上下限、情绪回落和记录，都由程序完成。
  - 模型可以自由提出难度、环境加成和数值变化（规则比较宽松）。
  - 角色本身的属性只从角色表里查，模型不能直接报。
- **变化由事件驱动。** 每一处变化都来自剧情里发生的事，并记下缘由。程序不会因为时间流逝或同处一个场景就自己改数值；唯一的例外是一时的情绪会慢慢回落（第 4 节）。
- **主角的感情由玩家决定。** 只记录别人对主角的态度，不记录、也不预设主角对别人的态度。
- **每个数字都能查到来历。**
  - 初始值附有原文依据。
  - 之后每次变化都有一条记录。记录跟着回复版本走，可以撤销。
- **做成内置插件「跑团」。** 没适配过的卡，或者预设里没有跑团条目，都完全不受影响。
- **不丢掉预设的破限。** 每一步都完整保留预设拼好的内容，只在末尾追加。

## 1. 一轮怎么跑

```
你发消息
  │
  ├─ 开着「检定绝对通过」→ 跳过第一步；处于聊天模式 → 整轮不跑跑团
  │
第一步：裁定（预设的请求 + 裁定说明，强制调用掷骰工具）
  │  模型列出这一轮的检定：谁、做什么、为什么说不准、用哪项属性、难度多少、有什么加成，
  │  再写好大成功、成功、失败、大失败四种结果各自会发生什么
  ├─ 程序掷骰，选出掷中的那一种结果
  ├─ 如果有检定要看前一个结果才能决定，程序把结果告诉模型，模型再申请一次（每轮最多来回 5 次）
  │
第二步：叙述（预设的请求 + 检定结果 + 写作要求）
  │  模型按掷中的结果写正文。正文照常显示
  │
第三步：结算（第二步的请求 + 刚写好的回复 + 结算说明，强制调用结算工具，在后台进行）
  │  模型回顾这段回复，逐个过一遍在场的角色：对主角的态度有没有变、
  │  角色之间的关系有没有变、有没有受伤或恢复、有没有新角色
  │
程序记账：更新数值，存进这个回复版本
```

- **换一版回复**：重新跑第二步和第三步，这一轮的裁定和骰子保持不变。每个版本从同一个起点各自结算。
- **改了自己的消息再重新生成**：消息内容变了，所以会重新裁定。
- **继续写**：沿用这一轮的裁定，写完后重新结算。
- **第一步失败**（接口报错，或者解析不出结果）：在提示词追踪里提示，然后按「本轮没有检定」继续第二步，不会卡住。
- **第三步失败**：自动重试一次；仍然失败时，回复下方提示「这一轮没有结算」，可以点「重新结算」。
- **下一条消息**：第三步还没做完时，会先等它做完，再开始下一轮。
- **结算为什么单独一步**：0.4.0 让模型在正文末尾顺带写结算，模型几乎总是忘记，数值很少变化。单独一步时，模型只做这一件事，并且要逐个角色填写，不容易漏。

## 2. 属性

### 通用属性

以普通成年男性为 100，数值按倍数理解：200 就是普通人的两倍。

| 属性 | 管什么 |
| --- | --- |
| 力量 | 搬、举、打、角力 |
| 敏捷 | 速度、灵巧、平衡、手上功夫、潜行 |
| 体质 | 耐力、扛伤、抗病、酒量 |
| 感知 | 察觉、观察、直觉 |
| 智力 | 知识、推理、学习 |
| 意志 | 定力、抗压、抵抗诱惑和恐吓 |
| 魅力 | 外貌和气质带来的吸引力、第一印象 |
| 口才 | 说服、谈判、欺骗、表演 |

AI 适配时按下面的参照表打分，模型判断时也对照这张表：

| 数值 | 大致水平 |
| --- | --- |
| 30 | 幼童 |
| 50 | 孩子、病弱、年迈 |
| 100 | 普通成年男性 |
| 150 | 受过训练 |
| 200 | 行业顶尖 |
| 300 | 人类极限 |
| 300 以上 | 超出人类 |

### 特长

特长按档位乘到属性上：

| 档位 | 倍率 |
| --- | --- |
| 未学 | ×0.5 |
| 入门 | ×1 |
| 熟练 | ×1.5 |
| 精通 | ×2 |
| 大师 | ×3 |

- 检定不涉及特长时，不乘倍率。
- 检定涉及某项特长，但角色没学过，按「未学」算。

### 卡片自己的属性

魔力这类普通人没有的能力，由卡片自己定义，同时写明「100 代表这个世界里什么水平」。

### 状态

受伤、醉酒、疲惫等临时状态，可以带一个属性倍率，比如「左臂刀伤：力量 ×0.8」。状态在结算时加上或去掉。

## 3. 掷骰

### 有效值

> 有效值 = 属性 × 特长倍率 × 状态倍率 × 环境加成

- 环境加成由模型提出，并写明理由。例如：工具趁手 ×1.2，黑暗中 ×0.7，对方信任你 ×1.3。
- 单项加成限制在 ×0.25～×4，所有加成相乘后限制在 ×0.1～×10。

### 成功率

> 成功率 = 有效值³ ÷（有效值³ + 难度³）

- **对抗**：把公式里的难度换成对方的有效值。
- **难度档**：简单 50，普通 100，困难 150，很难 200，极难 300。难度的含义是「属性要多高才有五成把握」。模型也可以给中间值。
- **上下限**：成功率限制在 1%～99%。
- **运气成分**：公式里的「3」可以在设置里调。数值越大，结果越看实力；越小，越看运气。

| 有效值 ÷ 难度 | 0.5 倍 | 0.67 倍 | 0.75 倍 | 相等 | 1.5 倍 | 2 倍 | 3 倍 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 成功率 | 11% | 23% | 30% | 50% | 77% | 89% | 96% |

### 掷骰和档位

每次检定掷一个 1～100 的数，成功线 S = 成功率 × 100：

| 档位 | 条件 |
| --- | --- |
| 大成功 | 掷出 ≤ max(1, round(S ÷ 10)) |
| 成功 | 掷出 ≤ S |
| 失败 | 掷出 > S |
| 大失败 | 掷出 > 100 − max(1, round((100 − S) ÷ 10)) |

举两个例子：
- 成功率 80%：1～8 大成功，9～80 成功，81～98 失败，99～100 大失败。
- 成功率 23%：1～2 大成功，3～23 成功，24～92 失败，93～100 大失败。

实力弱的人更容易大失败。

### 明骰和暗骰

- **明骰**：主角能感觉到结果的检定，比如撬锁、说服。显示在回复上方。
- **暗骰**：主角察觉不到的检定，比如守卫有没有注意到你、她是不是在说谎。默认不显示，可以在检查器里看。

## 4. 态度

### 只记录别人对主角的态度

每个角色对主角有六条线，各自 0～100，互不抵消：

**亲近、怨恨、信任、敬重、畏惧、吸引**

另外还有一项熟悉度，也是 0～100，表示这个角色对主角有多了解。

- 主角对别人的感情由玩家在剧情里表达，不记录，也不预设。
- 角色之间的关系不打分，用几个字记录现状，例如「表面客气，暗中提防」，并保留最近 5 条缘由。发生事件时由结算改写。

### 底色和一时情绪

每条线由两部分组成：底色加上一时波动。显示值是两者之和，限制在 0～100。

- **一次变化 Δ 分成两份。**
  - 进入底色的比例 = 0.2 + 0.6 ×（1 − 熟悉度 ÷ 100），剩下的进入一时波动。
  - 生人之间这个比例是 80%，一件事就能定下印象。老相识之间是 20%，一件事大多只是一时的情绪。
- **一时波动会回落。** 每轮往底色回落 15%。
- **越接近两头越难动，但不会动不了。**
  - 数值超过 50 以后继续往上，变化量乘以 0.4 + 0.6 ×（100 − 当前值）÷ 50。
  - 数值低于 50 以后继续往下，变化量乘以 0.4 + 0.6 × 当前值 ÷ 50。
  - 到了最边上仍然保留 40%。0.4.0 用的是不留余地的乘法，初次见面时信任只有 10 左右，被戳穿谎言也只降 1 点。
- **单轮上限**：一轮里每条线最多变化 ±30。

### 性格系数

每个角色有三项性格系数，默认 1，范围 0.5～2。它们影响这个角色对主角的态度怎么变，所以主角没有性格系数：

| 系数 | 作用 |
| --- | --- |
| 敏感 | 所有态度变化都乘以这个数 |
| 记仇 | 怨恨的一时波动回落速度除以这个数 |
| 多疑 | 信任上升时除以这个数，下降时乘以这个数 |

### 描述和缘由

程序按规则把数值翻译成文字描述，和数字一起交给模型：

| 条件 | 描述 |
| --- | --- |
| 亲近 ≥ 60 且 怨恨 ≥ 50 | 爱恨交织 |
| 畏惧 ≥ 60 且 亲近 ≥ 50 | 又怕又离不开 |
| 吸引 ≥ 60 且 怨恨 ≥ 50 | 恨，却又被吸引 |
| 亲近 ≥ 60 且 信任 < 30 | 喜欢但不信任 |
| 敬重 ≥ 60 且 亲近 < 30 | 敬而远之 |
| 六条线都 < 20 且 熟悉 < 20 | 陌生 |

上面这些组合都不满足时，就按最高的一两条线取词。完整的规则表写在代码里，可以调整。

每个角色的态度保留最近 5 条缘由，每条记下哪一轮、发生了什么事、哪条线怎么变。

## 5. 结算

结算是第三步：模型调用 `hearth_settle` 工具，按固定的表格填写这段回复造成的变化。

| 部分 | 内容 |
| --- | --- |
| `present` | 在场的角色（不含主角） |
| `attitudes` | 在场的每个角色各一项：六条线和熟悉度的变化，以及是哪件事。没有变化也要写一项，各条线填 0 |
| `bonds` | 角色之间的关系有了变化：现在的关系（几个字）和缘由 |
| `status` | 临时状态：加上（可以带属性倍率，例如「力量×0.8」）或去掉 |
| `new_characters` | 新登场、以后还会出现的角色，附估计的属性 |
| `growth` | 很少发生：属性的长期变化（每次最多 ±10），或特长换档 |

- **变化的大小和事件相称**，结算说明里给了参照：寒暄、日常交流 0～2；留下印象的举动 3～8；明显的好意或冒犯 8～15；重大事件 15～30。
- 态度变化由程序按第 4 节的规则执行，实际变化可能比模型写的小。被规则缩到 0 的变化不显示。
- 写到主角自己的态度时，这一项不执行，并在记录里说明。
- 第一步里冒出来的新角色（比如守卫），模型会先给一个临时数值，结算时可以正式建档。
- 填不对的项会被跳过，并在检查器里提示。
- 原文和每一项的结果都存在这个回复版本上。

### 旧的结算块

0.4.0 的叙述说明要求模型在回复末尾附一个隐藏的 `<结算>` 块。预设里还是旧条目（没有结算条目）时，跑团照旧从回复里读这个块，一行一条变化，并把它从正文里去掉：

```
<结算>
态度｜林晚→主角｜亲近+8 怨恨-3｜你替她挡了一刀
熟悉｜守卫甲→主角｜+10｜正面交过手
关系｜林晚与守卫甲｜结了仇｜他出卖了她
状态｜主角｜+左臂刀伤｜力量×0.8｜被守卫划了一刀
状态｜主角｜-醉意｜酒醒了
新角色｜守卫甲｜受过训练｜力量160 敏捷120 感知130｜后门守卫，三十来岁
属性｜主角｜口才+5｜长期练习
</结算>
```

面板的「跑团」页会提示「更新跑团条目」，更新后改为单独结算。

## 6. 主角视角和隐藏信息

**交给模型的说明会要求：**
- 以主角的视角写。
- 正文里不出现数字、属性名和「检定」这类字眼。
- 角色的态度通过言行流露出来。
- 不替主角决定他喜欢谁、恨谁。
- 暗骰的结果只能通过主角看得到、听得到的表现体现。

**界面上默认能看到多少：**

| 内容 | 默认 |
| --- | --- |
| 主角自己的属性、特长、状态 | 全部可见 |
| NPC 的属性 | 只显示大致水平，比如「受过训练」 |
| NPC 对主角的态度、NPC 之间的关系 | 隐藏，可以点「揭开」查看 |
| 暗骰 | 隐藏 |
| 结算 | 主角自己的变化直接显示；别人的态度变化只显示「某某记住了这件事」，点开才看到具体变化 |

模型能看到在场角色的全部数据，不在场的角色只看到名字和态度的大意，见第 8 节「跑团数据只带在场的角色」。

## 7. 卡片适配（编辑模式）

### 怎么用

编辑模式里有一个「数据化适配」按钮。点击后，AI 通读卡片和世界书，在回复里附一个 `<角色表>` 块。

### 角色表包括

- 主角和所有重要角色的属性、特长、初始状态，每个数值都附原文依据。主角之外的角色还有性格系数。
- 每个重要角色对主角的初始态度（六条线加熟悉度），附缘由。
- 重要角色彼此之间的关系，用几个字写现状，附缘由。
- 卡片自己的属性（如果有）。

### 规则

- AI 按第 2 节的参照表打分。主角的设定来自卡片对 {{user}} 的描述，以及你当前的用户角色。
- 不写主角对别人的态度。
- 和 AI 改卡一样，会显示修改前后的对比，可以撤销。
- 之后再改时只有写到的部分会变：属性、特长、性格按项合并，状态、别名、依据写了就整体替换；态度只改写到的线；关系按两个人整条替换。
- 可以接着对话让 AI 调整，比如「林晚的力量太高了」。
- 适配之前已经开始的对话，下一轮会自动用卡片数据初始化。已经有数值的对话不受影响，可以在角色面板里点「从卡片重新载入」。
- 用了 MVU 的卡：属性和态度由跑团负责，卡片原有的变量和状态栏照旧。适配时不改动 MVU 的条目。
- 0.4.0 适配的角色表里如果有主角对别人的态度，读入时会去掉；角色之间的数值态度会改写成一句关系。

## 8. 预设条目

预设里需要以下条目，可以在设置里查看和修改：

| 条目 | 标记 | 用在哪里 |
| --- | --- | --- |
| 跑团·裁定说明 | `<<<\|hearth\|ruling>>>` | 第一步 |
| 跑团·叙述说明 | `<<<\|hearth\|narrate>>>` | 第二步 |
| 跑团·结算说明 | `<<<\|hearth\|settle>>>` | 第三步 |
| 跑团·检定绝对通过说明 | `<<<\|hearth\|pass>>>` | 开着「检定绝对通过」时，代替检定结果 |

- 这些条目由跑团插件取走，不按普通条目发送。原因：带请求脚本的预设（例如小猫之神）会给普通条目记账，以此保住缓存。如果每一步各发各的条目，它会以为你每轮都在来回开关。
- 预设里没有裁定条目时，跑团不启动。在面板的「跑团」页点「加到当前预设」，会加上一套通用的条目。
- 适配过的预设可以带自己口吻的条目，以及每一步开头的一句话（`*-lead`），见[预设适配](presets.md#跑团条目)。
- 关闭跑团插件时要同时关掉这些条目，否则它们会被当成普通条目发给模型。

### 请求怎么改

三步都完整保留预设拼好的请求，只在末尾追加，所以前面的内容完全一样。接口支持缓存时，后两步更快、更省钱。

- **普通请求**：追加一条消息（角色和条目相同），内容是这一步的说明和跑团数据。
- **工具对话**（例如小猫之神的请求脚本把整个请求拼成工具对话，以 `context` 的同步结果结尾）：
  - 追加一个回合：`*-lead` 的一句话（可以没有）、一次 `context` 调用，调用结果是这一步的说明和数据。
  - 第三步在这之前先追加刚写好的回复，写成一次回复工具的调用，和预设脚本记录历史回合的方式相同。
- **工具**：三步都声明预设的工具加上 `hearth_check` 和 `hearth_settle`，只是强制调用的不同：第一步是 `hearth_check`，第二步是预设的回复工具，第三步是 `hearth_settle`。预设的回复工具认不出来时（例如它让模型自己选工具），第二步不加跑团的工具。
- 处于聊天模式（直接和 AI 聊天）时，整轮跳过跑团。判断依据是 Hearth 的回复模式。

### 跑团数据只带在场的角色

剧情里遇到过的角色都留在角色表里，但每一步只把在场角色的完整数据交给模型。这样跑团数据的长度取决于这一幕有几个人，而不是剧情里一共遇到过多少人。

在场的角色包括：

| 来源 | 说明 |
| --- | --- |
| 主角 | 始终在场 |
| 角色卡本身的角色 | 名字在角色表里时始终在场 |
| 最近 3 条回复的结算 | 结算的 `present` 里记下的角色 |
| 提到名字的角色 | 这一轮的用户消息、上一条回复（第一轮是开场白）里出现名字或别名的角色。第三步还看刚写好的回复。只查两个字以上的名字和别名 |
| 这一轮的检定 | 检定的执行者和对手，以及裁定时新登记的角色 |

- **在场的角色**照常写出属性、特长、状态、对主角的态度和最近的缘由。
- **角色之间的关系**只写两个人都在场的。
- **不在场的角色**写在末尾的「其他已登记的角色」里：名字，以及对主角态度的大意（第 4 节的描述，例如「有好感，信得过」）。模型因此知道他们已经登记过，不会当成新角色重新估计数值。
- 数据本身不受影响：结算、手动修改都作用在完整的角色表上。模型在检定里提到不在场的角色时，程序照样按角色表里的数值计算。

估算：每个在场角色约 220 字，每个不在场角色约 15 字。60 个角色、在场 4 人时，跑团数据从约 13600 字降到约 1800 字。

### 和小猫之神原有内容的冲突

小猫之神固定的开场思考里有一句「完全忽略那些无聊的表面数字」，本意是指年龄。为了不让模型连属性数值也忽略：
- 检定结果先写文字结论，数字放在括号里作为依据。
- 跑团数据开头写明「下面的数值是本轮的事实依据」。

## 9. 数据存放

| 内容 | 存在哪里 |
| --- | --- |
| 规则参数：属性清单、参照表、难度档、运气成分、回落速度等 | 插件设置（全局） |
| 卡片的角色表 | 角色卡的 `extra.hearth.rpg`。以后加卡片导出功能时，写进 ST 卡的 `data.extensions.hearth` |
| 本轮裁定：有哪些检定、掷出多少、选中了哪个结果 | 这条回复消息上，所有版本共用 |
| 实时数值：角色表、态度、关系、变化记录 | 每个回复版本上各存一份完整的。换版本、开分支时自动切换 |
| 结算：模型填写的原文、每一项的结果、在场的角色；进行中或失败的标记 | 这个回复版本上 |

## 10. 界面

- **检定条**：回复上方显示一行，比如 `撬锁 · 困难 · 23% · 掷出 61 → 失败`，前面是骰子图标。点开可以看理由、加成，以及四种结果里选中的那一种。暗骰默认收起成「暗骰 ×N」，点开才显示。
- **裁定进度**：裁定进行时，回复的位置先显示「正在裁定…」，然后逐个显示掷出的骰子。
- **结算提示**：回复下方。
  - 结算进行时显示「正在结算这一轮…」。
  - 完成后，主角自己的变化直接显示，例如「新状态「左臂刀伤」（力量×0.8）」；别人的态度变化显示为「林晚、守卫甲记住了这件事」，点开是每一项的变化和缘由。
  - 没有完成时显示「这一轮没有结算」和原因，带「重新结算」按钮。
- **输入框旁的开关**：「检定绝对通过」。只管一轮，发出后自动关掉。聊天模式下不显示。
- **角色面板**（检查器里的「跑团」页），包括：
  - 主角的属性和状态
  - 其他角色的大致水平
  - 他们对你的态度、角色之间的关系（默认隐藏，可以揭开）
  - 每条数值的变化记录

  数值可以手动修改。
- **提示词追踪**：每一步分开显示。第一步有多次来回时，每一次都能看到。
- 界面上不用表情符号。

## 11. 实现

### 插件

- 内置插件 `tabletop`，显示名「跑团」，`order` 设为 30。它排在酒馆助手（20）之后，所以 `onRequest` 拿到的是预设请求脚本（如小猫之神的 Stage 1）处理过的请求体。
- 文件：

| 文件 | 内容 |
| --- | --- |
| `src/plugins/tabletop/rules.ts` | 属性、参照表、有效值和成功率、掷骰档位（纯函数） |
| `attitude.ts` | 态度变化、回落、打折、性格系数、描述 |
| `sheet.ts` | 角色表格式（YAML 读写、校验）、实时状态 |
| `ruling.ts` | 第一步：工具定义、工具循环、文本退路 |
| `settle.ts` | 第三步：结算工具的定义和执行；旧的结算块 |
| `scene.ts` | 哪些角色在场，只有他们的完整数据交给模型 |
| `shape.ts` | 每一步怎样接到预设请求的末尾：普通请求和工具对话；三步共用的工具 |
| `entries.ts` | 通用的预设条目 |
| `index.ts` | 装配：三步的顺序、后台结算、「重新结算」 |

### 内核提供的支持

1. **`RequestContext` 包含以下字段：**
   - 本次生成的类型（normal / swipe / regenerate / continue）
   - `messageId`、`swipeId`
   - `send(body)`：用当前连接发一次请求，返回文本和工具调用；本次生成被中止时，它也一起中止
   - `progress(event)`：向界面推送进度
2. **`ChatMessage` 和 `Swipe` 的 `plugins?: Record<string, unknown>`**：按插件 id 存数据。
3. **回复之后的后台工作**：`onAfterReceive` 返回的 `background` 在回复保存并显示之后运行，结束时把修改写进对话，并通过生成的事件流发一次 `update`。同一个对话的下一次生成会先等它完成。另有 `api.send`，在生成之外用当前连接发请求；`registerAction` 给「重新结算」这样的按钮用。
4. **编辑模式的插件接口** `registerEditTask({ id, label, instruction, apply })`，由插件提供三样东西：
   - 一个按钮
   - 追加到编辑提示词里的说明
   - 对回复里自己那个块的处理：返回 ChangeSet，以及修改结果里要显示的前后对比
5. **界面**：
   - 消息上方的检定条、下方的结算提示
   - 检查器里由插件提供的分页
   - 裁定进度
   - 提示词追踪分步显示

   这些界面目前是跑团专用的组件，和酒馆助手的前端一样随主程序更新，不随插件自动更新。

### 第一步的工具

```json
{
  "name": "hearth_check",
  "parameters": {
    "think": "裁定前的简短判断",
    "checks": [{
      "actor": "主角，或角色名",
      "actor_value": 120,
      "action": "要做的事",
      "reason": "为什么结果说不准",
      "attribute": "力量…口才，或卡片自定义属性",
      "skill": "特长名（可选）",
      "difficulty": 150,
      "opponent": { "name": "守卫甲", "attribute": "感知", "skill": "", "value": 130 },
      "modifiers": [{ "reason": "只有一根发卡", "factor": 0.8 }],
      "hidden": false,
      "outcomes": { "critical": "…", "success": "…", "failure": "…", "fumble": "…" }
    }],
    "done": true
  }
}
```

**参数**
- `difficulty` 和 `opponent` 二选一。
- `actor_value` 和 `opponent.value` 只在这个角色还没有角色表时使用，程序会据此建一个临时档。
- 每个结果写一两句即可，以免第一步写得太长。

**工具返回**

每个检定返回：有效值（附计算过程）、成功率、掷出的数、档位，以及选中的那一种结果。

**循环和出错**
- `done` 为 false 时，程序把结果作为工具结果追加进去，再请求一次。最多来回 5 次；到了上限，就按已有的结果进入第二步。
- 接口不接受工具时，去掉工具，改为要求模型输出 `<hearth_check>` 包裹的 JSON，按同样的结构解析。

### 角色表格式（YAML）

```yaml
自定义属性:
  魔力: { 说明: 施法能力, 基准: 100 = 本世界一名合格的魔法学徒 }
角色:
  主角:
    属性: { 力量: 100, 敏捷: 115, 体质: 95, 感知: 120, 智力: 130, 意志: 110, 魅力: 105, 口才: 125 }
    特长: { 开锁: 精通 }
    状态: []
    依据: 开场白写主角是落魄的锁匠学徒，「手比脑子快」
  林晚:
    别名: [晚晚]
    属性: { 力量: 70, 敏捷: 130, 体质: 90, 感知: 140, 智力: 120, 意志: 150, 魅力: 160, 口才: 110 }
    特长: { 剑术: 熟练 }
    性格: { 敏感: 1.3, 记仇: 1.8, 多疑: 1.5 }
    依据: 设定写她「自幼习剑」「记仇，一笔一笔都记着」
态度:
  - 从: 林晚
    对: 主角
    亲近: 60
    怨恨: 55
    信任: 25
    敬重: 40
    畏惧: 0
    吸引: 45
    熟悉: 85
    缘由: [三年前主角不告而别]
关系:
  - 之间: [林晚, 沈掌柜]
    现状: 表面客气，暗中提防
    缘由: [沈掌柜曾把林家的消息卖给仇家]
```

- 「态度」的「对」固定是主角，可以省略。
- 实时状态在这份结构上再加三样东西：一时波动、缘由记录、临时角色。
